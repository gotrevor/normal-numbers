## The finding

Last lap found that kernel `Array.getD` on a literal is `O(index)`, which made
the run sweep quadratic, and fixed it with balanced if-trees.  **The certificate
half was worse and for the same reason.**  `emit_hitting_lean.py` was emitting

* `live` as `[...].contains j` — a linear kernel scan;
* `rho`, `omega`, `forced` as `List.lookup` on literal association lists — three
  more linear scans.

`checkCertA` does ~5 such lookups per edge over `A·M` edges, so the certificate
sweep was `O(A·M²)`.  At `M = 5328` that is why `(2,5)`'s `Cert0` was still
running at 7½ minutes last lap.

Fixes, both in `experiments/emit_hitting_lean.py`:

1. **`134b3a9`** — all four tables as balanced if-trees on `j`, `O(log M)`.
2. **`4ba4b46`** — (a) the trees RUN-compressed: `live/rho/omega/forced` are
   constant over long stretches, so leaves are maximal constant runs, not
   indices (`Cert0` source 1.09 MB → 113 KB); (b) the monolithic
   `checkCertA … := by decide +kernel` replaced by `checkEdgesOnA` chunks glued
   with `checkEdgesOnA_of_chunks` plus one `checkForcedA` — the
   `HittingSetBase7.lean` pattern, now emitted automatically.  `CERTCHUNK`
   picks the largest divisor of `M` below it (the glue proves `0 (k*c)`, so the
   chunk size MUST divide `M`; `5328 = 2^4·3^2·37`).

Nothing is trusted: a wrong tree or a wrong chunking can only fail a `decide`,
never fake a proof.
